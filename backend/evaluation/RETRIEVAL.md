# 本地检索命中率基线

在 `backend` 中运行：

```powershell
python evaluation/retrieval.py --version baseline-20261013 --repeat 3
```

默认使用 `retrieval_cases.json` 的固定查询，直接调用当前 `products.service.search`，只读 MySQL。使用本地缓存的 BGE 模型，强制离线；在结果目录根据商品快照建立临时 Chroma 索引，不读写应用原索引，不调用 DeepSeek、Tavily 或 LangSmith。无需启动前后端。单独统计模型加载、临时索引准备和预热后的查询耗时。

标注由当前本地商品 ID、规格和价格人工确定，不使用被测 `eligible` 或 `matches_model` 生成正确答案。`state` 是预先标注的需求，测的是检索层；本评测不测自然语言需求提取、首字等待或回答质量。它不能替代完整 Agent 评测。

## 保存的指标

| 指标 | 定义 |
|---|---|
| 指定同款命中率 | 所有指定型号都有符合条件的目标商品返回；不存在商品的请求也计入分母。 |
| 库内可满足请求的同款命中率 | 只统计标注中所有目标都有符合条件商品的指定型号请求，用于区分缺库和检索漏召回。 |
| 同系列候选提供率 | 有已标注、符合条件的同系列商品时，是否提供该商品；当前未实现同系列召回，这部分作为缺失能力的基线。 |
| 无结果率 | 成功执行的查询中，商品和同系列候选均为空的比例。失败不冒充无结果。 |
| 意外无结果率 | 标注存在相关候选的查询中，未返回任何候选的比例。 |
| 硬条件违反率 | 非空查询中存在品类、品牌排除、预算或规格违反的比例；同时输出商品级违反率。型号正确性单独由标注 ID 检查。 |
| Recall@3 / Precision@3 | 前三个返回商品对人工标注相关商品的召回比例 / 正确比例，按查询平均。 |
| 检索耗时 P50/P95 | 预热后的查询耗时；逐条保存 SQL、Embedding、Chroma 查询耗时。初始化耗时独立保存。 |
| 首字耗时 | null：本评测不调用生成模型，不能补造首字统计。 |

## 结果与对比

结果默认保存到项目根目录 `log/<时间>-retrieval-<版本哈希>/`，已被 Git 忽略。本次基线位于 `log/retrieval-baseline-20261013/`：

- `manifest.json`：代码版本、数据集哈希、商品/价格哈希、Embedding 配置、初始加载与索引准备耗时。
- `facts.json`：本轮本地商品和价格快照，不包含账号、会话或密钥。
- `runs.jsonl` / `results.csv`：每个问题的正确 ID、实际 ID、是否命中、违反条件和分阶段耗时。
- `summary.json`：汇总、分组统计和失败案例。
- `vectors/`：独立测试索引；保留用于追溯，不参与应用检索。

后续优化使用同一组问题复测：

```powershell
python evaluation/retrieval.py --version optimized-v1 --repeat 3 --baseline ../log/retrieval-baseline-20261013
```

`comparison.json` 会核对数据、模型、重复次数和统计模式，条件不一致时不输出可比差值。商品数据新增或变化后应先更新人工标签；不存在的商品今后入库时，原来的“缺库”标签也需要复核。固定小样本与重复执行不代表真实用户请求分布，不据此声称整体命中率。
